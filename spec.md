# 1. PRODUCT VISION

## 1.1 Overview

AI Mystery Room is a web application that allows users to create and solve fictional mystery investigations generated by artificial intelligence.

A user enters a short scenario, story idea, or mystery premise. The AI transforms that input into a complete investigation containing:

- A fictional crime or mysterious incident.
- A set of suspects, each with a believable background and motive.
- An investigation timeline.
- AI-generated evidence, such as chat conversations, photographs, CCTV-style stills, witness statements, and documents.
- Hidden clues, contradictions, and misleading evidence.
- One predetermined culprit.
- A final accusation interface.
- An explanation of the solution after the user submits an accusation.

The user explores the case, examines the evidence, connects clues, and identifies the culprit.

The experience should feel like a digital detective investigation rather than a standard question-and-answer chatbot.

## 1.2 Core Product Principle

**The AI creates the mystery. The user investigates it.**

The culprit and underlying truth must be determined before the evidence is presented to the user. Evidence must be consistent with that truth.

The application must never change the culprit retroactively to match the user's answer.

## 1.3 Example User Experience

A user enters:

"A famous college student disappears during a cultural festival. Four people were seen near the auditorium that night."

The application generates a fictional case containing:

1. The incident report.
2. Four suspects and their profiles.
3. WhatsApp-style fictional conversations.
4. CCTV-style evidence from several locations.
5. Witness statements.
6. A chronological timeline.
7. Contradictions between suspect statements and evidence.
8. A final accusation form.

The user selects a suspect, submits the accusation, and receives a verdict explaining the decisive clues.

All people, messages, places, and events in generated investigations are fictional unless explicitly supplied by the user as fictional material.

# 2. PRODUCT GOALS

## 2.1 Primary Goals

1. Allow users to generate a playable mystery from a short text prompt.
2. Generate logically consistent cases with a fixed culprit and solution.
3. Provide an immersive investigation interface.
4. Present evidence in different formats, not only plain text.
5. Allow users to inspect suspects, evidence, and timelines.
6. Evaluate the user's final accusation against the predetermined solution.
7. Explain the solution using evidence that appeared in the investigation.
8. Save investigations and their progress for later continuation.
9. Provide a polished, responsive, desktop-first experience that also works on mobile.
10. Make the application maintainable, testable, and extensible.

## 2.2 Success Criteria

The MVP is successful when:

- A user can enter a scenario and generate a complete case.
- The backend validates and stores the case.
- Every generated case has exactly one canonical culprit.
- Evidence supports the solution without impossible contradictions.
- Users can inspect every available clue.
- The final accusation produces the correct verdict and explanation.
- Cases persist in MongoDB and can be reopened.
- API failures, malformed AI output, and image-generation failures are handled gracefully.
- The application does not expose Gemini credentials or private solution data through public APIs.
- The application works on current desktop and mobile browsers.

# 5. CORE GAMEPLAY RULES

These rules are mandatory and must be treated as product invariants.

## 5.1 Fixed Solution

Every case must contain exactly one canonical culprit.

The culprit must be selected during case planning, before the final evidence package is generated.

The stored solution is immutable after the case becomes playable.

If the generation process fails validation, regenerate or reject the case before publishing it.

## 5.2 Fair Play

Every solvable case must contain sufficient evidence to identify the culprit.

A solution must not depend on information that was never shown to the user.

The user must not need external knowledge, real-world research, or random guessing to solve the case.

## 5.3 Evidence Consistency

All evidence must be consistent with:
- The canonical incident.
- The culprit's actions.
- The timeline.
- Suspect statements.
- The physical locations involved.
- The known relationships between suspects.

Contradictions are permitted only when they are intentional and explained by the canonical solution.

For example, a suspect may lie about their location, but the contradiction must be deliberate and useful to the investigation.

## 5.4 Unique Culprit

The system must reject a case if:
- Two suspects are equally supported as the culprit.
- The solution depends on an undisclosed clue.
- The evidence directly disproves the canonical solution.
- The canonical solution cannot explain major evidence.
- The final verdict cannot be justified using presented clues.

## 5.5 Verdict Rules

- Correct suspect selected: verdict is `correct`.
- Incorrect suspect selected: verdict is `incorrect`.
- An invalid or unrelated suspect ID is rejected.
- A case can be accused against only once by default.
- The original accusation and result must be stored.
- Repeated submission must not change the original result.

The MVP should not impose a time limit or penalize users for inspecting evidence.

# 6. USER FLOW

## 6.1 Main Flow

1. User opens the landing page.
2. User selects "Create a Mystery".
3. User enters a scenario.
4. User selects difficulty and optional generation settings.
5. User submits the form.
6. The backend validates the request.
7. The backend asks Gemini to generate the case plan.
8. The backend validates the plan and establishes the canonical solution.
9. The backend generates the evidence package.
10. The backend validates consistency and completeness.
11. The completed case is stored in MongoDB.
12. The user is redirected to the investigation room.
13. The user explores suspects and evidence.
14. The user records notes and marks clues.
15. The user selects a culprit.
16. The backend evaluates the accusation.
17. The result page displays the verdict and solution explanation.

## 6.2 Failure Flow

If generation fails:
- Preserve the original scenario input.
- Display a useful error message.
- Allow retrying the generation request.
- Do not create a playable case with an invalid solution.
- Do not charge a second generation quota for an idempotent retry.
- Record a sanitized internal failure reason.

If an image fails:
- Display a designed placeholder.
- Preserve the textual evidence.
- Allow retrying image generation when appropriate.
- Never invalidate the entire case solely because a decorative image failed.

## 8.1 Visual Direction

Build a premium detective investigation interface.

Suggested design direction:
- Dark charcoal background.
- Muted slate panels.
- Off-white text.
- Amber or warm gold accents.
- Restrained red for danger indicators.
- Subtle borders.
- Atmospheric shadows.
- Clean typography.
- Small, purposeful animations.
- Clear information hierarchy.

Avoid excessive neon, generic AI landing-page gradients, excessive glassmorphism, and cluttered dashboards.

The application should look like a polished digital detective workstation.

## 8.2 Landing Page

Required sections:
1. Navigation bar with logo and primary action.
2. Hero section with the heading "Every Mystery Has a Truth."
3. Supporting description.
4. Primary CTA: "Create a Mystery".
5. Secondary CTA: "Explore How It Works".
6. Feature section explaining AI-generated cases.
7. Three-step explanation: Create, Investigate, Solve.
8. Example evidence previews using clearly fictional sample content.
9. Footer with project information and privacy disclaimer.

The hero CTA must navigate to `/create`.

## 8.3 Mystery Creation Page

Fields:
- Scenario description: required textarea.
- Category: optional selection.
- Difficulty: required selection with a default.
- Tone: optional selection.
- Case length: required selection with a default.

Recommended values:

**Category**
- Any
- Disappearance
- Theft
- Murder mystery
- Cyber mystery
- Historical mystery
- Campus mystery
- Locked-room mystery

**Difficulty**
- Easy
- Medium
- Hard

**Tone**
- Classic detective
- Psychological thriller
- Noir
- Lighthearted mystery

**Case length**
- Short
- Standard
- Extended

Suggested defaults:
- Category: Any
- Difficulty: Medium
- Tone: Classic detective
- Case length: Standard

Suggested scenario limit: 30–2,000 characters.

The interface must show a character counter and prevent submission of empty or over-limit scenarios.

Display a warning that real people's private information must not be submitted.

## 8.4 Generation Progress Page

Display the current generation stage, using server-reported status where available.

Suggested stages:
- Understanding the scenario.
- Creating suspects.
- Establishing the solution.
- Building the evidence.
- Checking consistency.
- Preparing the investigation.

Progress messages must represent actual backend stages. Do not display fabricated percentages or claim completion before the case is ready.

Allow the user to wait, cancel where supported, or retry after a recoverable failure.

## 8.5 Investigation Dashboard

Layout:
- Case title and incident summary.
- Case status and difficulty.
- Incident overview.
- Suspect count.
- Evidence count.
- Investigation progress.
- Recent evidence.
- Timeline preview.
- Quick navigation to Suspects, Evidence, Timeline, and Notes.
- Persistent "Make an Accusation" action.

Do not reveal the canonical culprit in the dashboard.

## 8.6 Suspect Directory

Each suspect card must display:
- Fictional portrait or avatar.
- Name.
- Age, if generated.
- Occupation or role.
- Relationship to the incident.
- Publicly available alibi.
- Known motive summary.
- Relevant evidence count.

Do not expose private solution fields, hidden motives, or internal suspicion scores.

A suspect's displayed profile must be based only on the public suspect data stored in the case.

## 8.7 Evidence Gallery

Evidence must be organized by category.

Categories:
- Messages.
- Images.
- CCTV.
- Documents.
- Witness statements.
- Physical clues.
- Other.

Each card must display:
- Evidence title.
- Evidence type.
- Discovery time or event time, where appropriate.
- Short description.
- Related suspect IDs, if publicly relevant.
- Investigation status.

Users must be able to filter by evidence type and search by title or text.

## 8.8 Evidence Detail Viewer

Provide a dedicated detail view or modal.

Display:
- Full evidence content.
- Original fictional timestamps.
- Source and context.
- Associated suspects.
- Associated timeline events.
- Evidence-specific metadata.
- A "Mark as Investigated" control.
- A "Save Note" control.
- Previous and next evidence navigation where available.

For images, use a responsive image viewer.

For messages, display a readable fictional chat interface.

For CCTV-style evidence, display a still image with a camera label, fictional timestamp, and scene description.

Never imply that a generated still image is actual recorded footage.

## 8.9 Timeline

Display case events chronologically.

Each event contains:
- Timestamp.
- Event title.
- Event description.
- Evidence references.
- Related suspect IDs, if relevant.

Support a list or vertical timeline layout.

The timeline must use a consistent timezone policy. Fictional case timestamps must not be silently converted into the user's real local time in a way that changes their meaning.

## 8.10 Notes and Clue Tracking

Users must be able to:
- Add investigation notes.
- Edit their notes.
- Delete their notes.
- Mark evidence as investigated.
- Track which clues they have reviewed.

Notes must belong to the case owner.

Notes must not be sent to Gemini unless a future feature explicitly requires it and the user is informed.

## 8.11 Accusation Page

Show all suspects as selectable options.

The user must select exactly one suspect before submission.

Include:
- Suspect selection.
- Optional explanation field.
- Confirmation step.
- Submit accusation button.

Optional explanation length: up to 1,000 characters.

Do not reveal whether a suspect is correct before the accusation is submitted.

The server evaluates the selected suspect ID. The client must never calculate the verdict.

## 8.12 Results Page

Display:
- Correct or incorrect verdict.
- User's selected suspect.
- Actual culprit.
- Summary of what happened.
- Motive and method.
- Key evidence supporting the solution.
- Explanation of misleading clues.
- Timeline reconstruction.
- Replay or return-to-library actions.

The result must be derived from the stored canonical solution, not generated from scratch after the accusation.

For incorrect accusations, explain the correct reasoning without changing the original result.

# 9. TECHNICAL ARCHITECTURE

## 9.1 System Overview

React frontend → Express API → Authentication and authorization → Case service → Gemini integration → Validation and consistency checks → MongoDB persistence → Sanitized API response.

Image-generation requests must be handled through a separate provider adapter or service boundary.

Gemini must never be called directly from the browser using a private API key.

## 9.2 Frontend

Use:
- React.
- Vite.
- React Router.
- TypeScript.
- A consistent styling system, preferably Tailwind CSS.
- A reusable component library built around the project's visual system.
- TanStack Query or an equivalent data-fetching solution.
- A schema validation library such as Zod for frontend forms.

Use a consistent API client rather than scattering raw fetch requests throughout components.

Frontend state should be divided into:
- Server state: cases, suspects, evidence, results.
- Local UI state: selected filters, modal visibility, current tab.
- Persisted user state: investigation progress and notes, stored through the backend.

Do not treat local storage as the authoritative database.

## 9.3 Backend

Use:
- Node.js.
- Express.js.
- TypeScript.
- Mongoose.
- Zod or an equivalent runtime schema validation library.
- The official supported Google Gen AI SDK for Gemini.
- A centralized error-handling middleware.
- Structured logging with secrets and sensitive information redacted.

Keep controllers thin. Business logic belongs in services.

## 9.4 Database

Use MongoDB with Mongoose schemas and indexes.

Store:
- Users or guest sessions.
- Mystery cases.
- Case generation jobs or generation state.
- Accusation results.
- Investigation progress.
- User notes.

Use embedded documents for bounded case data when that makes consistency and retrieval easier. Use separate collections for data that needs independent lifecycle management, such as generation jobs or user sessions.

## 9.5 External Services

Required:
- MongoDB database.
- Gemini API credentials.

Optional:
- Object storage for generated images.
- A compatible image-generation provider.
- Email provider if account recovery is implemented.

Do not make an optional image provider a hard dependency for creating a playable case.

# 11. DATA MODEL

All database documents must include creation and update timestamps where appropriate.

Use MongoDB ObjectIds or another consistent identifier strategy. API identifiers must be serialized consistently.

## 11.1 User

```ts
type User = {
  _id: ObjectId;
  email?: string;
  displayName?: string;
  authProvider?: string;
  createdAt: Date;
  updatedAt: Date;
};
```

A user account is optional for the guest-first MVP.

## 11.2 Guest Session

```ts
type GuestSession = {
  _id: ObjectId;
  tokenHash: string;
  expiresAt: Date;
  createdAt: Date;
};
```

Store only a hash of the guest session token where practical.

Use a secure, random token and an HttpOnly cookie. Never trust a user-supplied owner ID as proof of ownership.

## 11.3 Mystery Case

```ts
type MysteryCase = {
  _id: ObjectId;
  ownerId: ObjectId;

  title: string;
  scenario: string;
  category: string;
  difficulty: "easy" | "medium" | "hard";
  tone: string;
  caseLength: "short" | "standard" | "extended";

  status:
    | "queued"
    | "generating"
    | "validating"
    | "ready"
    | "failed";

  incident: {
    summary: string;
    incidentType: string;
    location: string;
    incidentTime: string;
    background: string;
  };

  suspects: Suspect[];
  evidence: Evidence[];
  timeline: TimelineEvent[];

  solution: {
    culpritId: string;
    motive: string;
    method: string;
    reconstruction: string;
    decisiveEvidenceIds: string[];

  generation: {

    promptVersion: string;

  publishedAt?: Date;
  createdAt: Date;
  updatedAt: Date;

```

**Security requirement:** This is the internal server model. Never serialize the entire document directly to a public API response.

## 11.4 Suspect

```ts
type Suspect = {

  age?: number;
```

`clueRole` is an internal field. Remove it from public evidence responses unless a specific result view is allowed to disclose it.

The evidence must be written in a way that permits users to infer its significance instead of explicitly labeling every clue.

## 11.9 Asset

```ts
type Asset = {
  _id: ObjectId;
  caseId: ObjectId;
  ownerId: ObjectId;

  kind: "portrait" | "evidence_image";
  status: "pending" | "ready" | "failed";

  storageKey?: string;
  mimeType?: string;

  provider?: string;
  createdAt: Date;
  updatedAt: Date;
};
```

Do not assume a model-generated image can be stored directly in MongoDB as an unrestricted binary field. Prefer object storage or a suitable local development storage adapter.

## 11.10 Data Validation

Validate all AI-generated documents before persistence.

Required invariants:
- Every suspect ID is unique within a case.
- Exactly one culprit ID exists.
- The culprit ID references an existing suspect.
- Every evidence ID is unique.
- Every evidence relationship references a valid suspect or timeline event.
- Every decisive evidence ID references an existing evidence item.
- Every timeline reference is valid.
- No required field is empty.
- Timestamps are valid and chronological where applicable.
- The solution is supported by the published evidence.
- Public serializers omit solution secrets and internal validation fields.

# 12. GEMINI INTEGRATION

## 12.1 Integration Principles

Gemini is responsible for generating fictional mystery content.

The server is responsible for:
- Choosing the supported model through configuration.
- Sending prompts.
- Handling timeouts and retries.
- Parsing structured responses.
- Validating the output.
- Maintaining the canonical truth.
- Enforcing game rules.
- Storing the case.
- Controlling what information is revealed to the user.

Never assume that valid JSON automatically means a logically valid mystery.

## 12.2 Recommended Generation Pipeline

Use a staged generation pipeline rather than requesting every detail in one unstructured prompt.

### Stage 1: Scenario planning

Input:
- User scenario.
- Category.
- Difficulty.
- Tone.
- Case length.

Output:
- Case title.
- Incident premise.
- Suspects.
- Canonical culprit.
- Motive.
- Method.
- Incident timeline.
- Core facts.
- Expected decisive clues.
- Planned red herrings.

This is an internal object.

### Stage 2: Evidence generation

Generate the evidence based on the approved plan.

Include:
- Suspect messages.
- Witness statements.
- Incident documents.
- Image descriptions and image prompts.
- CCTV-style scene descriptions.
- Physical evidence.
- Timeline-linked events.

Every evidence item must reference the plan's existing IDs and facts.

The evidence generation stage must not independently choose a new culprit.

### Stage 3: Consistency validation

Check:
- Timeline contradictions.
- Alibi consistency.
- Evidence references.
- Culprit identity.
- Whether the clues support a unique solution.
- Whether the story contains accidental alternative explanations.
- Whether the user has sufficient information to solve the case.

### Stage 4: Repair

If the validator finds a repairable issue, ask Gemini to correct the affected material while preserving the canonical solution.

Do not let repair rewrite the culprit.

### Stage 5: Publication

Only after all required validation passes:
- Save the completed case.
- Mark the case `ready`.
- Make public case endpoints available.
- Expose only sanitized data to the frontend.

If validation fails after the configured repair attempts, mark the generation as failed.

## 12.3 Structured Output

Use the Gemini SDK's supported structured-output or JSON-schema capabilities where available.

Define schemas in the application and validate every response with Zod or an equivalent validator.

Do not rely solely on extracting JSON with regular expressions.

If the model returns malformed output:
1. Attempt a bounded repair or retry.
2. Revalidate the complete object.
3. Fail safely if validation still fails.

## 12.4 Prompt Design

Maintain versioned prompt templates in `server/src/prompts/`.

Every prompt must have:
- A version.
- A clearly defined task.
- The input schema.
- The required output schema.
- Constraints.
- Examples where useful.
- Explicit instructions not to invent references to missing entities.
- Instructions to preserve the canonical solution.

Use separate prompts for planning, evidence generation, and consistency repair.

## 12.5 Example Case-Planning Prompt

```text
You are the mystery architect for a fictional detective game.

Create a solvable mystery from the user's scenario.

Requirements:
1. Generate one and only one canonical culprit.
2. Establish the culprit before generating evidence.
3. Create a coherent motive, method, and timeline.
4. Create distinct suspects with believable motives and alibis.
5. Design multiple clues that collectively identify the culprit.
6. Include plausible red herrings that can be explained by the truth.
7. Make the case solvable using only the information that will be shown.
8. Do not rely on arbitrary coincidences or undisclosed evidence.
9. Use stable, unique IDs for suspects, events, and planned clues.
10. Keep the content fictional and avoid using real private information.
11. Match the requested difficulty, tone, and case length.
12. Return only data conforming to the requested schema.

The canonical solution is internal game data. Never include it in
the public case overview or public suspect responses.
```

This prompt is a starting point, not a replacement for formal schemas and server-side validation.

## 12.6 Difficulty Requirements

**Easy**
- Three suspects.
- Six to eight evidence items.
- Direct clues.
- Limited timeline complexity.
- At least two independent clues supporting the culprit.

**Medium**
- Four suspects.
- Nine to twelve evidence items.
- Multiple connected clues.
- At least one meaningful contradiction.
- Plausible red herrings.

**Hard**
- Five or six suspects.
- Thirteen to eighteen evidence items.
- Interconnected timeline and alibis.
- Multiple stages of deduction.
- Red herrings that can be disproved.
- No dependence on inaccessible information.

Case length may increase the narrative depth, but difficulty must be controlled independently of story length.

These counts are generation targets, not permission to publish an inconsistent case. If the selected difficulty cannot meet the requirements, the case must be repaired or rejected.

## 12.7 Gemini Configuration

Use environment variables for:
- API key.
- Model ID.
- Request timeout.
- Maximum generation attempts.
- Repair attempts.
- Output token budget.
- Rate limits.

Choose a supported Gemini model based on current API availability, structured-output support, image capabilities, quality, latency, and cost.

Do not hardcode a model name throughout the application.

## 12.8 Cost and Reliability

- Limit input and output tokens.
- Set request timeouts.
- Use bounded exponential backoff for transient failures.
- Do not retry permanent validation or authorization failures.
- Avoid generating the same case twice on network retries.
- Store generation state.
- Make generation requests idempotent.
- Record provider usage metadata where available.
- Enforce per-user or per-session generation limits.

# 13. AI-GENERATED IMAGES AND CCTV

## 13.1 Important Provider Distinction

Text generation and image generation must be treated as separate capabilities.

Do not assume the selected Gemini model supports generating image files merely because it supports image understanding.

Use Gemini for image prompts or scene descriptions when needed. Generate the actual image through a supported image-generation model or provider.

Implement the image provider behind an interface so it can be changed without rewriting the case-generation service.

## 13.2 Image Types

The MVP may support:
- Fictional suspect portraits.
- Evidence photographs.
- CCTV-style stills.
- Location illustrations.

Text-only evidence must always remain playable.

## 13.3 Asset Generation Workflow

1. Create the evidence record.
2. Generate a visual prompt from the approved case plan.
3. Send the prompt to the configured image provider.
4. Receive the image.
5. Validate its format and size.
6. Store the image in object storage.
7. Save the asset reference.
8. Display the image through an authorized URL or backend route.

If image generation fails, the evidence remains available as text.

## 13.4 Image Safety and Presentation

- All generated evidence must be clearly fictional in the interface.
- Do not use real people's identities without authorization.
- Avoid unnecessary graphic violence.
- Do not fabricate actual surveillance footage or claim that fictional evidence is authentic.
- Use a CCTV-style visual aesthetic, not an assertion of real recording.
- Apply suitable content moderation and provider restrictions.

# 14. REST API SPECIFICATION

Use the `/api/v1` prefix.

All endpoints must use consistent JSON responses and centralized error handling.

## 14.1 Standard Response Format

Success:

```json
{
  "success": true,
  "data": {},
  "message": "Request completed successfully"
}
```

Failure:

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The supplied request is invalid",
    "details": []
  }
}
```

Do not expose stack traces, provider secrets, raw internal prompts, or hidden solution data in error responses.

## 14.2 Health

`GET /api/v1/health`

Returns:
- API status.
- Database connectivity status where appropriate.
- Application version.

Never return credentials or infrastructure secrets.

## 14.3 Case Generation

`POST /api/v1/cases`

Request:

```json
{
  "scenario": "A student disappears during a college festival.",
  "category": "campus_mystery",
  "difficulty": "medium",
  "tone": "classic_detective",
  "caseLength": "standard"
}
```

Behavior:
- Validate input.
- Authenticate or establish guest ownership.
- Enforce generation limits.
- Create an idempotent generation job.
- Return the case or generation resource.

Recommended response for asynchronous generation: HTTP `202 Accepted`.

```json
{
  "success": true,
  "data": {
    "caseId": "CASE_ID",
    "status": "queued"
  }
}
```

The frontend then polls the status endpoint.

## 14.4 Generation Status

`GET /api/v1/cases/:caseId/status`

Returns:
- Case ID.
- Generation status.
- Current stage.
- A safe error code if failed.
- Retry eligibility where appropriate.

Must not return the internal solution.

## 14.5 List Cases

`GET /api/v1/cases`

Returns only cases owned by the current authenticated user or guest session.

Support pagination and optional filters.

## 14.6 Get Case

`GET /api/v1/cases/:caseId`

Returns:
- Public case details.
- Public suspects.
- Timeline summary.
- Evidence summary.
- Investigation progress.

Must not return the canonical solution or internal clue classifications.

## 14.7 Suspects

`GET /api/v1/cases/:caseId/suspects`

Returns public suspect information.

`GET /api/v1/cases/:caseId/suspects/:suspectId`

Returns a single public suspect profile.

## 14.8 Evidence

`GET /api/v1/cases/:caseId/evidence`

Supports:
- Category filtering.
- Search.
- Pagination.

`GET /api/v1/cases/:caseId/evidence/:evidenceId`

Returns the full public content of the selected evidence item.

## 14.9 Timeline

`GET /api/v1/cases/:caseId/timeline`

Returns a chronologically ordered list of events with public evidence references.

## 14.10 Investigation Progress

`GET /api/v1/cases/:caseId/progress`

Returns the current user's investigation state.

`PATCH /api/v1/cases/:caseId/progress`

Updates:
- Investigated evidence IDs.
- Other explicitly supported progress fields.

Validate that every evidence ID belongs to the requested case.

## 14.11 Notes

`POST /api/v1/cases/:caseId/notes`

Creates a note.

`PATCH /api/v1/cases/:caseId/notes/:noteId`

Updates a note.

`DELETE /api/v1/cases/:caseId/notes/:noteId`

Deletes a note.

Validate note lengths and case ownership.

## 14.12 Accusation

`POST /api/v1/cases/:caseId/accusations`

Request:

```json
{
  "selectedSuspectId": "SUSPECT_03",
  "explanation": "The timestamp contradicts the suspect's alibi."
}
```

The backend must:
1. Confirm ownership.
2. Confirm the case is ready.
3. Validate the selected suspect.
4. Atomically enforce the one-accusation rule.
5. Compare the selection with the stored canonical culprit ID.
6. Persist the verdict.
7. Return the authorized result payload.

## 14.13 Results

`GET /api/v1/cases/:caseId/result`

Available only after an accusation has been submitted, unless an explicit replay mode is introduced later.

Returns:
- Verdict.
- Correct culprit.
- Solution reconstruction.
- Decisive evidence and explanations.
- Red-herring explanations.

## 14.14 Delete Case

`DELETE /api/v1/cases/:caseId`

Deletes an owned case and associated progress, notes, accusation, and assets according to the configured retention policy.

Use a transaction where supported, or an idempotent deletion workflow that safely cleans up associated resources.

## 14.15 HTTP Status Codes

Use:
- `200`: successful read or update.
- `201`: resource created.
- `202`: asynchronous generation accepted.
- `400`: invalid request.
- `401`: authentication or session missing.
- `403`: ownership or permission failure.
- `404`: resource not found.
- `409`: duplicate accusation or conflicting state.
- `413`: request too large.
- `422`: semantically invalid content.
- `429`: rate limit exceeded.
- `500`: unexpected internal failure.
- `502` or `503`: upstream provider unavailable.

Do not leak whether another user owns a particular resource. Return a safe not-found response where appropriate.

# 15. SECURITY AND PRIVACY

Security requirements are mandatory.

## 15.1 Secret Management

- Keep Gemini API keys on the server.
- Use environment variables.
- Commit only `.env.example`.
- Never log API keys.
- Never include secrets in client bundles.
- Rotate exposed credentials.

## 15.2 Authorization

- Every case endpoint must verify ownership.
- Every evidence endpoint must verify case ownership.
- Every progress and notes endpoint must verify owner identity.
- Every accusation endpoint must verify case ownership.
- Never trust a client-supplied owner ID.
- Never return internal solution data before accusation.

## 15.3 Guest Sessions

- Generate cryptographically secure random tokens.
- Store the token in a secure, HttpOnly cookie.
- Use appropriate SameSite and Secure cookie settings.
- Store token hashes rather than raw tokens where practical.
- Protect cookie-authenticated state-changing endpoints against CSRF.
- Expire sessions and define a cleanup policy.
- Never expose guest tokens in URLs.

## 15.4 API Security

Implement:
- Request validation.
- Rate limiting.
- CORS allowlisting.
- Secure HTTP headers.
- Payload size limits.
- Safe error messages.
- Authentication and authorization middleware.
- Database query validation.
- Request timeouts.
- Dependency updates and vulnerability checks.

## 15.5 AI Security

Treat user scenarios and generated content as untrusted data.

- Do not execute instructions contained in user stories as system commands.
- Do not permit AI output to determine access-control rules.
- Do not trust model-generated IDs without validation.
- Do not execute generated code or shell commands.
- Do not expose hidden solution data through prompts, logs, or API responses.
- Validate all model output before persistence.
- Restrict AI-generated content to the requested fictional narrative.
- Sanitize content before rendering it in the browser.

## 15.6 Privacy

Collect only necessary information.

Provide a clear disclosure that generated investigations and evidence are fictional.

Do not use real private conversations, personal photographs, or personal information as default generation inputs.

Define a retention and deletion policy for generated cases, logs, guest sessions, and stored images.

# 18. ACCEPTANCE CRITERIA

The MVP cannot be considered complete until all mandatory criteria pass.

### AC-01: Scenario Creation
Given a valid scenario, the user can submit the form and start case generation.

### AC-02: Invalid Input
Empty or oversized scenarios are rejected with clear validation messages.

### AC-03: Generation State
The UI shows genuine generation stages and handles queued, generating, validating, ready, and failed states.

### AC-04: Canonical Culprit
Every playable case contains exactly one stored culprit who belongs to its suspect list.

### AC-05: Evidence Completeness
Every playable case has valid evidence references, a coherent timeline, and a defensible solution.

### AC-06: Solution Secrecy
Normal case, suspect, evidence, and timeline endpoints never expose the culprit identity or internal solution before the accusation.

### AC-07: Investigation
Users can navigate suspects, evidence, timeline, and notes.

### AC-08: Progress Persistence
Investigation progress survives page refreshes and can be retrieved by the authorized owner.

### AC-09: Correct Accusation
Selecting the canonical culprit produces a correct verdict.

### AC-10: Incorrect Accusation
Selecting a different valid suspect produces an incorrect verdict and preserves the canonical solution.

### AC-11: Duplicate Submission
Concurrent or repeated accusation requests cannot produce multiple final accusations.

### AC-12: Authorization
A different session cannot access another user's cases, evidence, notes, progress, or results.

### AC-13: AI Failure
A failed generation never becomes a playable, incomplete case.

### AC-14: Image Failure
A failed image request does not prevent textual evidence from being investigated.

### AC-15: Responsive UI
Core functionality remains usable on mobile, tablet, and desktop.

### AC-16: Security
No Gemini key or private solution data is present in public frontend responses.

### AC-17: Automated Tests
Critical business rules and the main user workflow have automated coverage.

### AC-18: Documentation
A new developer can install dependencies, configure environment variables, start the application, and run tests using the README.

# 22. IMPORTANT ENGINEERING DECISIONS

These decisions are authoritative unless this specification is explicitly revised.

1. **Guest-first:** users must be able to play without mandatory registration.
2. **Server-side AI:** Gemini calls must happen on the backend.
3. **Fixed culprit:** the canonical solution is established before evidence generation.
4. **Staged generation:** planning, evidence generation, validation, repair, and publication are separate steps.
5. **Validated JSON:** AI output must conform to runtime schemas.
6. **Private solution:** canonical solution fields must never be exposed through ordinary public APIs.
7. **Server-side verdict:** the backend alone determines the result.
8. **Persistent progress:** notes and investigation progress must survive refreshes.
9. **Graceful image degradation:** a missing image cannot make a case unplayable.
10. **MERN stack:** React, Node.js, Express, and MongoDB are the core stack.
11. **Gemini integration:** use the official supported SDK through a provider adapter.
12. **No premature extras:** multiplayer, subscriptions, voice features, and public sharing are out of MVP scope.
13. **TypeScript:** use it for frontend and backend implementation.
14. **Automated tests:** critical business rules must be testable without live AI requests.
15. **Single source of truth:** `SPEC.md` governs the implementation.

# 24. FINAL PRODUCT DEFINITION

AI Mystery Room is a web-based detective game in which users supply a fictional premise, receive a complete AI-generated investigation, inspect clues across multiple evidence formats, and accuse one suspect.

The application succeeds by combining two systems:

**The mystery engine**
- Establishes the truth.
- Generates suspects and evidence.
- Maintains a coherent timeline.
- Validates the case.
- Evaluates the accusation.

**The investigation experience**
- Presents the evidence.
- Helps users explore and connect clues.
- Preserves notes and progress.
- Reveals the solution after the accusation.

Neither system can substitute for the other.

A beautiful interface without a consistent mystery is incomplete. An intelligent mystery generator without an engaging investigation interface is also incomplete.

The MVP is complete only when both systems work together from scenario submission to final verdict.
